# Автотесты формы авторизации Stellantis AutoCRM

Проект содержит четыре функциональных UI-теста на PHP, пример подготовки пользователя напрямую в БД, пример API-запроса на создание пользователя и перечень дополнительных сценариев.

Проверки привязаны к устойчивым атрибутам формы (`id`, тип поля и видимый текст), а не к порядку элементов на странице. Тексты и маршруты сверены с `https://stellantis.autocrm.ru/` 18 сентября 2026 года.

## Покрытие задания

| Требование | Реализация |
|---|---|
| Неверные логин и пароль | `loginWithInvalidCredentialsShowsGenericError` |
| Пустые поля | `emptyFormShowsValidationError` |
| Маскирование пароля | `passwordIsMasked` |
| Ссылка «Забыли пароль» | `forgotPasswordLinkOpensRecoveryForm` |
| Создание пользователя через БД | `TestUserHelper` и `PdoUserDatabase` |
| Работа без настоящей БД | `TestUserHelperTest` с in-memory реализацией |
| API-запрос создания пользователя | `CreateUserRequest` и `examples/create_user.php` |
| Дополнительные сценарии | `ADDITIONAL_SCENARIOS.md` |

## Состав

- `tests/Functional/LoginFormTest.php` — неверные данные, пустые поля, маскирование пароля, восстановление пароля;
- `src/Support` — хелпер тестового пользователя, интерфейс БД и PDO-реализация с параметризованными запросами;
- `tests/Unit/TestUserHelperTest.php` — работа хелпера без настоящего подключения к БД;
- `examples/valid_login_setup.php` — как подключить хелпер к тестовой БД перед авторизацией и удалить данные после теста;
- `examples/create_user.php` — пример `POST`-запроса к API;
- `ADDITIONAL_SCENARIOS.md` — дополнительные проверки.

## Требования

- PHP 8.2 или новее с расширениями `curl` и `json`;
- Composer;
- Docker для рекомендуемого запуска Chromium/Selenium либо уже запущенный Selenium Server.

Сайт использует промежуточную JavaScript-проверку браузера. Поэтому контейнер запускает обычный Chromium внутри виртуального дисплея, а не headless-режим. При первом открытии форма может появиться не сразу.

Функциональные тесты обращаются к внешнему стенду. Для ежедневной CI-проверки отдельно выделен быстрый unit-набор, не зависящий от сети, Selenium и состояния сайта.

## Быстрый запуск

```bash
composer install
docker compose up -d selenium
composer test
docker compose down
```

Только быстрые unit-тесты, без браузера и внешней сети:

```bash
composer test:unit
```

Только функциональные тесты:

```bash
composer test:functional
```

Ожидаемый результат полного прогона: 6 тестов и 20 assertions.

Адрес стенда и Selenium можно переопределить переменными окружения:

```bash
BASE_URL=https://stellantis.autocrm.ru \
SELENIUM_URL=http://localhost:4444/wd/hub \
composer test:functional
```

## Хелпер пользователя

`TestUserHelper` принимает абстракцию `UserDatabase`. В unit-тесте используется память, поэтому реальная БД не нужна. В интеграционном примере `PdoUserDatabase` выполняет параметризованный `INSERT`, возвращает учетные данные тесту и удаляет созданную запись в `finally`.

Перед применением к реальному проекту нужно согласовать имена таблицы/полей и алгоритм хеширования с текущей схемой приложения. Учетные данные БД передаются только через переменные окружения и не попадают в репозиторий.

## Пример API

```bash
API_BASE_URL=https://stellantis.autocrm.ru \
API_CREATE_USER_PATH=/api/v1/users \
API_TOKEN=replace_with_test_token \
php examples/create_user.php
```

Публичная спецификация API в задании не дана. Поэтому путь, поля тела, способ авторизации и ожидаемый код `201` оформлены как явно настраиваемый пример. Перед реальным запуском их следует сверить с OpenAPI/Swagger или внутренним контрактом сервиса. Токен в коде не хранится.

## Наблюдение по валидации

На текущем стенде пустая форма валидируется на клиенте двумя сообщениями: `Необходимо заполнить «Электронная почта».` и `Необходимо заполнить «Пароль».` Неверная пара учетных данных обрабатывается сервером и возвращает общее сообщение `Некорректный email / пароль`. Язык принудительно задается параметром `language=ru_RU`, чтобы результат не зависел от cookie предыдущей сессии.

## Принятые ограничения

- В задании нет валидных учетных данных, поэтому успешная авторизация перечислена как дополнительный сценарий, но не автоматизирована против рабочего стенда.
- Схема БД не предоставлена: имена таблицы и полей в PDO-примере демонстрационные и должны быть согласованы с тестовой схемой проекта.
- Контракт API не предоставлен: URL, тело запроса, авторизация и ожидаемый код ответа вынесены в конфигурацию.
